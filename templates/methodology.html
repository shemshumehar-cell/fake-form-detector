Why Passive Analysis is Safer & Legally Sound

In cybersecurity, testing is divided into two primary disciplines: Active Penetration Testing and Passive Security Auditing.

Passive Analysis (Our Approach)

  • Issues only standard HTTP GET requests (identical to any normal web browser).
  • Never submits forms, alters database records, or transmits exploit payloads.
  • Zero risk of application crash, data corruption, or service outage.
  • Complies with computer crime statutes (CFAA, Computer Misuse Act).

Active Exploitation (Forbidden)

  • Sends fuzzing payloads, brute-force attempts, or SQL injections.
  • Can cause database drops, server crashes, or account lockouts.
  • Illegal without prior explicit written authorization from system owners.
  • Stricly avoided by Fake Form Detector.

✅ What The Scanner Checks

  • Transport Layer Encryption: HTTPS enforcement, TLS status, and redirect preservation.
  • HTTP Security Headers: CSP, HSTS, X-Content-Type-Options, Referrer-Policy, and Permissions-Policy.
  • HTML Form Architecture: Form methods (GET vs POST), action destinations, and mixed-content targets.
  • Credential Hygiene: Plaintext password input transmissions over unencrypted channels.
  • File Upload Surfaces: Detection of <input type="file"> without restrictive guardrails.
  • CSRF Token Heuristics: Discovery of anti-CSRF token hidden fields in state-changing forms.

❌ What The Scanner Cannot Check

  • Dynamic SQL Injection Exploits: Static HTML cannot confirm whether the database query uses prepared statements.
  • Dynamic Cross-Site Scripting (XSS): Passive inspection cannot prove lack of server-side output escaping without sending test payloads.
  • Authenticated Business Logic Flaws: Inaccessible without executing real logins.
  • Zero-Day Server Vulnerabilities: Underlying OS, memory corruption, or kernel weaknesses.
  • Internal Network Topologies: Firewall rules or backend microservice communications.

OWASP Top 10 Conceptual Mapping

The Open Web Application Security Project (OWASP) defines the critical risks facing modern applications. Here is how Fake Form Detector aligns with core OWASP categories:

A02:2021 – Cryptographic Failures:

Addressed by detecting plaintext HTTP transport, missing HSTS enforcement, and credentials transmitted over unencrypted channels.

A05:2021 – Security Misconfiguration:

Addressed by auditing missing HTTP headers (Content-Security-Policy, X-Content-Type-Options: nosniff, Referrer-Policy, and Permissions-Policy).

A01:2021 – Broken Access Control & A04:2021 – Insecure Design:

Addressed by checking for Anti-CSRF token presence, sensitive data exposure in HTTP GET URLs, and unprotected file upload entry points.

A03:2021 – Injection (Context & Limitations):

Identifies user-controllable input surfaces and explicitly reminds developers that parameterized queries and output escaping are required, avoiding false vulnerability claims.

Educational Use & Penetration Testing Disclaimer

The Fake Form Detector score is a defensive heuristic designed to educate developers and students on essential security hygiene. It is not a substitute for comprehensive manual code reviews, threat modeling, or authorized full-scope penetration tests.
